# 渐进式迁移计划

## 1. 基本原则

迁移采用绞杀者模式：网关逐步将已迁移路径转发到新服务，未迁移路径继续由单体处理。
每个阶段必须可独立部署、验证和回退；原单体目录 `../calles` 在未获得明确指令前只读，
不得作为重构副作用被修改。

## 2. 阶段与交付条件

| 阶段 | 工作范围 | 完成条件 | 回退方式 |
| --- | --- | --- | --- |
| 0. 基线 | 工程骨架、Compose、Nacos、构建脚本 | 所有模块构建通过，基础设施配置可校验 | 删除新工程构建产物即可 |
| 1. 网关与认证 | 网关路由、JWT、登录/刷新/注销、旧 Header 适配 | 新旧 Token/接口约定明确，认证集成测试通过 | 网关把认证路径切回单体 |
| 2. 用户 | 账户资料、关系、用户设置与数据迁移 | 所有权表清单完成，读写与回退演练通过 | 停止 user 路由和双写，回到单体 |
| 3. 内容与文件 | 视频、标签、分类、上传和 MinIO 元数据 | 上传、读取、发布链路端到端通过 | 内容路径切回单体，保留对象兼容访问 |
| 4. 审核 | 审核任务事件、消费幂等、人工审核接口 | 重试/死信/重复消息测试通过 | 停止消费并回退至单体审核任务 |
| 5. 互动 | 点赞、收藏、评论、关注、历史、分享 | 幂等、计数一致性和限流测试通过 | 路由切回单体，保留事件重放能力 |
| 6. 推荐 | 用户画像与推荐结果投影 | 事件回放、降级推荐和性能指标达标 | 网关返回单体/静态降级结果 |
| 7. 拆库 | 逐服务物理数据库 | 数据校验、只读切换、灾备与回退预案通过 | 在明确窗口内恢复原数据源 |

## 3. 每个领域的迁移清单

开始一个服务前，必须补充以下记录到对应需求或设计说明中：

1. 原单体 Controller、Service、Mapper、表和 Redis Key 的清单。
2. API 输入输出、鉴权规则、调用方和兼容性策略。
3. 表的当前拥有者、目标服务、目标表名及是否需要回填。
4. 同步依赖与异步事件，包含发布方、消费方、路由键和失败策略。
5. 切流开关、监控指标、验证步骤和明确的回退操作。

不具备上述清单时，只能进行代码勘察或编写设计文档，不能开始数据迁移和流量切换。

## 4. 认证优先的实施顺序

认证是第一个业务迁移域，建议按以下最小切片推进：

1. 从单体梳理用户登录、管理员登录、注册、退出和改密接口，以及现有 `token`、
   `Authorization`、`adminToken` Header 的实际使用范围。
2. 在 `auth-service` 实现用户身份校验的服务边界；初期可通过受控适配读取旧用户数据，
   但不能让其他新服务直接访问旧用户表。
3. 实现 JWT 声明、签名、验签、刷新会话和注销失效，密钥仅由运行环境注入。
4. 在网关实现白名单与 Token 校验，向下游传递经过验证的主体上下文；业务服务保留
   防御性校验。
5. 为旧客户端提供有限期 Header 兼容层，并记录删除条件。
6. 建立登录成功、过期、刷新、注销、禁用、权限不足和伪造 Token 的测试矩阵。

认证尚未完成前，其他服务只可提供不需要真实身份的探针或内部占位接口。

## 5. 数据迁移策略

默认采用“先读、后双写、再切读、最后停旧写”的步骤：

```text
盘点与校验 -> 历史数据回填 -> 双写 -> 新服务读校验 -> 网关切读 -> 停旧写 -> 清理适配层
```

- 回填必须可重复执行，并记录批次、数量、校验和与失败记录。
- 双写期间要定义主写方和冲突处理规则，不能让两个系统无约束地同时修改同一事实。
- 切读前应对数量、主键集合、关键字段和最近变更进行校验。
- 原始数据和迁移脚本都不能因切流而立即删除；清理只在稳定观察期结束后执行。

## 6. 事件迁移策略

审核和推荐的迁移从事件契约开始，而不是从消费者代码开始。每个事件在实施前必须确定：

| 项目 | 要求 |
| --- | --- |
| 事件名 | 领域、动作和版本，例如 `content.published.v1` |
| 生产方 | 唯一拥有该业务事实的服务 |
| 消费方 | 明确的业务用途，禁止“可能会用”订阅 |
| 幂等键 | `eventId` 或等价的唯一业务键 |
| 可靠性 | Outbox、重试次数、死信队列与人工处理方式 |
| 演进 | 新旧版本并存期和下线条件 |

## 7. 验证与发布

每次迁移至少执行：模块构建、单元测试、服务启动探针、关键 API 集成测试、重复事件测试
（如适用）以及回退演练。发布后关注错误率、P95 延迟、消息积压、死信数量、鉴权失败率和
数据校验差异。阈值和观察窗口由具体迁移任务确定并记录。

## 8. 迁移完成定义

不要以“代码已拆分”作为迁移完成的判断。只有服务边界和数据所有权已记录、API/事件契约已
版本化、数据校验与回退已验证、认证和幂等已覆盖、关键监控与追踪已生效，并且旧实现的兼容期
和删除条件已记录后，才能标记该领域完成迁移或进入正式切流。完整清单见根目录 `AGENTS.md`
的“迁移完成定义”。
