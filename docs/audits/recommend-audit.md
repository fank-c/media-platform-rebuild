## 当前边界

- 推荐服务只输出推荐决策和视频短码，不管理视频元数据、审核状态或互动计数。
- 视频候选池的进入、下线和封禁状态由 content-service 领域事件驱动；用户画像、反馈流水和用户屏蔽属于 recommend-service 自属数据。
- 点赞、收藏、分享、合格观看和完播由 interaction-service 核验后通过 `interaction.video-action` 进入推荐侧；客户端行为反馈链路已删除，主动推荐屏蔽使用 `/api/recommend/blocks`。
- 首页推荐流支持游客模式和登录用户模式；登录用户可使用 Redis 待看缓冲池，游客直接实时计算。
- 推荐交互事件消费队列已经声明并实现幂等处理，但 interaction-service 的正式 Outbox 派发仍由环境开关控制，真实 RabbitMQ 联调尚未在本清单中视为完成。

## P1

### REC-01 下架事件路由键不一致，主动下架视频不会移出候选池

- **位置**：`RecommendMessagingConfiguration.VIDEO_OFFLINE_ROUTING_KEY`、`recommendVideoOfflineBinding()`、`VideoLifecycleConsumer`、`CandidateVideoApplicationService.handleOffline()`。
- **原问题**：content-service 主动下架事件使用路由键 `content.video.offline`；recommend-service 误绑定 `content.video.offlined`。
- **修复事实**：推荐侧常量、绑定、注释和测试已统一为 `content.video.offline`，没有双路由；真实消费者与应用服务执行后候选状态为 `OFFLINE`，重复消费状态不变。决策见 [ADR-0011](../adr/0011-recommend-offline-event-contract.md)。
- **原影响**：创作者主动下架的视频无法到达推荐生命周期队列，`recommend_candidate_video` 仍可能保持 `ACTIVE`，后续推荐请求可能继续返回已经下架的作品。管理员封禁事件 `content.video.banned` 不受此问题影响。
- **判断**：这是已经由代码和契约文档确认的跨服务契约问题，不是仅凭运行日志推断。
- **处理方向**：在当前开发阶段统一采用一个路由键，推荐与 content 的事件类型、绑定配置、消息模型、测试和文档同步修改；不保留两个新旧路由长期并存。修改跨服务事件契约时应同步 ADR 或现有事件契约记录。
- **验证证据**：`VideoOfflineContractTest` 覆盖绑定对象、真实消费用例和内存持久化替身的状态幂等；`VideoLifecycleConsumerTest`、`CandidateVideoApplicationServiceTest` 回归通过。
- **剩余边界**：真实 RabbitMQ 送达和 MySQL 落库尚未联调，因此保留“已实现待验收”。已有 Redis 缓冲的出队复核已实现，联调验证见 REC-02，本项不承诺缓冲立即失效。

### REC-02 Redis 待看缓冲出队时不复核候选状态和用户屏蔽

- **位置**：`RecommendFeedBufferService.consumeFeed()`、`pushToBuffer()`。
- **原问题**：登录用户从 Redis 队列 `LPOP` 出推荐物料后直接返回；缓冲物料只在生成时过滤，出队时不会再次复核。队列 TTL 默认为 1 小时。
- **修复事实**：首轮出队和有限补取共用复核方法，只接受 ACTIVE 候选，并检查 VIDEO、AUTHOR、TOPIC 三种屏蔽。主题按完整标签 ID 交集匹配，忽略空标签及两端空白；无效物料不放回队列。满额返回保留 `hasMore=true`，队列暂时为空不表示候选真正耗尽。
- **反馈修复证据**：测试候选改用 `createPublished()`，解决不存在的五参数构造器导致的编译错误；仓储替身的补取不重复返回已出队物料。新增主题首轮/补取过滤、取空队列但补水尚未完成、缓冲与实时结果都为空的回归测试。推荐模块 157 项测试通过。
- **验证边界**：使用真实缓冲服务及 Redis、仓储替身，尚未完成真实 Redis / MySQL 联调，不承诺复核之后的并发状态变化即时可见。
- **原影响**：视频进入缓冲后如果被下架、封禁或被用户新增屏蔽，仍可能在缓冲过期前继续返回给用户。推荐候选状态和用户屏蔽状态的变化不能立即反映到已经生成的物料中。
- **判断**：由当前出队实现和模块文档直接确认，尚未通过真实 Redis 环境复现最长暴露时长。
- **处理方向**：出队后对候选状态和用户屏蔽执行轻量复核；无效物料直接丢弃，不重新放回队列，并在数量不足时补充实时召回。需要同时明确新增屏蔽是否要求清空用户队列，避免将一致性要求扩大为全量即时失效。
- **验收条件**：物料入队后变为 `OFFLINE`、`BANNED` 或命中用户屏蔽时，下一次出队不再返回；无效物料不会因补水再次进入同一用户队列。

### REC-03 非法参数和缺少登录身份可能返回 500

- **位置**：`RecommendFeedController` 的屏蔽端点，以及 `RecommendExceptionHandler`。客户端反馈端点已在后续清理中删除。
- **原问题**：未知 `actionType`、未知 `blockType` 和缺少登录身份都通过 `IllegalArgumentException` 抛出，业务错误无明确 HTTP 映射。
- **修复事实**：新增 `RecommendExceptionHandler` 和独立 `MissingIdentityException`。业务参数、请求体校验、JSON 解析及参数类型转换错误返回 `400`；三个屏蔽端点缺少身份返回 `401`；未知故障返回 `500` 通用提示。统一使用 `ApiResponse`，`code` 与 HTTP 状态一致，`data=null`，不回显输入和内部异常。
- **原影响**：客户端无法稳定区分参数错误、未登录和服务端异常；业务输入错误可能按未处理异常返回 `500`，不符合推荐接口文档中约定的 `400/401` 语义。
- **验证证据**：`RecommendHttpErrorTest` 通过 MockMvc 执行真实控制器、校验器和异常处理器，覆盖非法反馈枚举、添加/撤销屏蔽非法枚举、请求体校验、畸形 JSON、查询参数错误、三个屏蔽端点缺少身份及未知异常。编译与推荐模块全部 155 项测试通过。
- **验证边界**：原验证为服务内 MVC HTTP 契约测试，不是经网关启动联调。后续清理删除了 feedback 接口；当前回归继续覆盖屏蔽与 feed 错误契约，并确认旧入口未映射。
- **处理方向**：建立 recommend-service 统一异常处理，将参数和枚举错误映射为 `400`，缺少身份映射为 `401`，资源或业务冲突按明确契约映射；响应仍使用公共 `ApiResponse` 外壳，不泄露内部异常。
- **验收条件**：屏蔽接口缺少身份返回 `401`；非法请求体返回统一的 `400`；未知异常返回 `500`；已删除入口不再接受行为。

### REC-04 客户端播放时长完全参与画像判断，信号可被伪造

- **原问题**：推荐 HTTP 反馈用客户端传入的播放时长直接更新画像，并与互动观看事实和推荐屏蔽职责重叠。
- **处理决策与事实**：删除客户端反馈端点、专用应用服务、请求 DTO 和客户端动作枚举；移除 `IMPRESSION`、`PLAY`、`SKIP`、`DISLIKE` 动作及建表约束中的对应值。保留 MQ 事件消费、行为流水表和 `/blocks`。
- **验证证据**：`RecommendHttpErrorTest` 确认旧反馈入口返回 `404`；`FeedbackActionContractTest` 拒绝旧客户端动作并约束热度只统计有效观看；原 MQ 视频及作者事件测试继续回归。
- **边界**：没有新增曝光、跳过或推荐批次结算能力；不修改互动服务的观看与计数语义，不执行实际数据库变更。

### REC-05 未消费视频解封事件，候选池无法自动恢复

- **位置**：`RecommendMessagingConfiguration`、`VideoLifecycleMessage`、`VideoLifecycleConsumer`、`CandidateVideoApplicationService`。
- **当前事实**：recommend-service 当前绑定 `content.video.offline` 和 `content.video.banned`，没有绑定或处理 `content.video.unbanned`。`CandidateVideoApplicationService` 可以在收到重新发布事件时把非 ACTIVE 候选重新激活，但 content-service 解封流程只发送 `unbanned`，不会重新发送 `published`。
- **影响**：视频被管理员封禁后，即使后续解封，recommend 候选状态仍保持 `BANNED`，不会重新进入推荐流。
- **判断**：由当前消息绑定、消息模型和模块文档确认，尚未做真实 RabbitMQ 解封事件演练。
- **处理方向**：为解封建立明确的当前事件契约，消费后将候选从 `BANNED` 恢复为 `ACTIVE`；恢复前应再次确认视频发布准入和候选必要快照。不能把 `unbanned` 简单当作任意状态的强制激活。
- **验收条件**：`BANNED` 候选收到合法解封事件后恢复为 `ACTIVE`；重复事件幂等；被主动下架或仍不满足发布条件的视频不会因解封事件错误入池。

### REC-06 推荐消费缺少明确的有界重试、死信和告警出口

- **位置**：`InteractionEventConsumer`、`VideoLifecycleConsumer`、`RecommendMessagingConfiguration`、recommend-service `application.yml`。
- **当前事实**：畸形 JSON、缺失关键字段、未知事件类型和不支持版本会被记录后正常返回，属于安全丢弃；部分业务异常会重新抛出，交给监听容器处理。但 recommend-service 没有在当前模块配置中明确声明统一的最大重试次数、死信交换机、死信队列和告警出口。
- **影响**：不可恢复消息与临时数据库异常的处理边界不清晰。非法消息可能只留下日志；业务异常最终是否重试、重试多久、何时进入死信依赖外部默认配置，难以审计和告警，也可能造成消息长期阻塞或静默丢失。
- **判断**：代码中缺少明确的 recommend 消费侧重试和死信配置是已确认事实；实际监听容器默认行为尚未通过 RabbitMQ 运行环境验证。
- **处理方向**：先区分不可恢复的契约毒丸和可重试的基础设施异常；前者记录原因后进入可查询的死信或隔离队列，后者配置有界指数退避，耗尽后进入死信并告警。不能将生产端 Outbox 的重试次数直接当作消费端重试策略。
- **验收条件**：格式错误、未知版本、未知事件类型和数据库瞬时异常分别有确定处理结果；超过重试上限的消息可在死信队列中查询，并包含 `eventId`、`traceId` 和失败原因；正常消息不被毒丸阻塞。

## P2

### REC-07 热度召回使用推荐反馈流水，不使用互动公开计数

- **位置**：`TrendingRecallChannel`、`FeedbackLogRepository.findTopVidsByPlays()`。
- **当前事实**：热度通道按 `recommend_feedback_log` 近 24 小时的 `WATCH_VIEW_QUALIFIED` 事件次数统计热门视频；同会话的 `WATCH_COMPLETED` 不再计数。这是有效观看热度，不等同于互动服务起播计入的公开播放量。
- **影响**：统计依赖登录用户有效观看事件的送达情况；游客不产生该事件。公开播放量和有效观看热度仍是不同口径，是否进一步组合特征不在本次清理范围。
- **判断**：这是明确的当前设计边界，不是 interaction 计数实现错误。是否切换口径需要先确定“热度”代表公开播放量、推荐消费量，还是两者组合。
- **处理方向**：优先通过 interaction-service 批量统计接口读取已汇总公开计数；如仍需保留推荐侧消费质量，应将其作为独立排序特征，不要混称为播放热度。跨服务同步调用需定义超时、重试上限和按零值降级方式。
- **验收条件**：热度口径写入推荐策略文档；统计服务不可用时有明确降级；热榜排序不会因客户端反馈重复或伪造直接突破约束。

### REC-08 缺少相关推荐接口

- **位置**：recommend-service 当前 HTTP 控制器和网关路由；计划接口为 `GET /api/recommend/videos/{vid}/related`。
- **当前事实**：当前只有首页推荐流和用户屏蔽接口，没有基于锚点视频的相关推荐接口。Qdrant 视频向量和候选池已经存在，相关能力尚未对外编排。
- **影响**：播放页无法直接使用推荐服务获取相似视频，客户端只能依赖首页推荐或自行实现相关推荐，视频向量能力没有覆盖播放页场景。
- **状态说明**：这是规划能力缺口，不是当前已发布接口的行为回归，不应与 REC-01 等契约错误同等优先处理。
- **处理方向**：后续若纳入范围，应明确锚点视频可见性、候选状态过滤、作者和主题屏蔽、本人作品过滤、结果去重、超时降级以及游客访问策略，再确定 HTTP 契约和网关路由。
- **验收条件**：只返回当前可推荐候选；锚点视频不存在或不可推荐时有明确响应；Qdrant 超时能够降级，不阻塞播放页主流程。

## 总结

当前 recommend-service 共有 8 项已记录问题或能力缺口：

- **6 项 P1**：REC-01 至 REC-06；REC-03、REC-04 已解决，其余保留原状态。
- **2 项 P2**：REC-07 热度口径和 REC-08 相关推荐能力。

建议推进顺序：

1. 验收 REC-01 下架事件送达与落库，后续补齐 REC-05 解封生命周期；
2. 验收 REC-02 缓冲出队复核（REC-03 错误映射已解决）；
3. REC-04 已通过删除客户端反馈链路解决，不再讨论客户端播放信号权重；
4. 在 RabbitMQ 联调时一并验收 REC-06；
5. 最后按产品优先级决定 REC-07 热度口径和 REC-08 相关推荐。

- REC-01 已实现待真实 RabbitMQ / MySQL 联调验收；REC-03、REC-04 已解决，其余问题保持原范围与状态。
- 客户端反馈清理同步将热度统计改为有效观看事件口径；REC-02 出队复核及本轮三项审查反馈已修复，真实基础设施联调未完成。解封消费或消费重试未处理。
