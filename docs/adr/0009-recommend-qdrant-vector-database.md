# ADR 0009: 推荐服务引入 Qdrant 向量数据库与双模向量化引擎

## 状态

**Accepted（已采纳，追认）**。该决策在提交 `7e8b5a3`（落地特征向量化流水线与 Qdrant 双模闭环）及 `059d726`（升级特征向量至 1024 维）落地时已生效，本文补齐架构决策记录。

## 背景

推荐服务（`recommend-service`）的核心职责是为全平台用户提供低延迟、高相关性的个性化视频推荐流（Feed）。其多路召回体系中，核心个性化召回（PersonalizedRecallChannel）与探索召回（ExploreRecallChannel）均依赖基于用户偏好向量与视频特征向量的近似最近邻（ANN, Approximate Nearest Neighbor）检索计算。

在引入向量存储基础设施前，面临以下技术瓶颈与选型约束：

1. **关系型数据库计算瓶颈**：MySQL 等关系型数据库无法对高维稠密向量建立专用空间索引（如 HNSW、IVF）。若在应用层全表拉取并在 JVM 内进行余弦相似度计算，计算复杂度为 $O(N)$，随着视频候选集扩大，CPU 迅速打满且响应延迟呈线性暴增，无法满足推荐流 100ms 内的端到端 SLA 要求。
2. **轻量化部署与本地开发闭环**：平台既要支持微服务独立容器化部署，又要兼顾本地无网或低成本单机快速拉起验证的需求，禁止引入动辄数 GB 内存和复杂分布式依赖的笨重集群。
3. **外网与模型依赖韧性**：线上计算特征向量若完全依赖外部 AI 大模型 API（如 OpenAI），可能因网络抖动、凭据过期、配额超限或离线开发而导致视频发布流水线中断，必须具备无缝降级能力。

## 决策

1. **向量数据库选型：Qdrant**
   - 选用开源向量搜索引擎 **Qdrant**。
   - 理由：基于 Rust 构建，性能卓越且极其轻量（单容器冷启动仅消耗约 200MB 内存）；原生提供完善的 HTTP/REST API 与 gRPC 接口；原生高效支持余弦相似度（Cosine Distance）；支持携带结构化 Payload 并在 ANN 检索阶段进行高效过滤。
2. **部署架构与独立实例所有权**
   - 部署模式：独立 Docker 服务（默认暴露 REST 6333 端口，gRPC 6334 端口），由 `recommend-service` 独占管理，不向外部微服务共享，遵循单一基础设施所有权原则。
3. **集合配置与向量维度选型（1024 维）**
   - 集合名称（Collection）：`video_vectors`；
   - 距离度量（Distance Metric）：`Cosine`（余弦相似度）；
   - **向量维度统一定为 1024 维**：
     - 在表征精度与内存/检索开销之间取得最佳平衡；
     - 主流嵌入模型（如 OpenAI `text-embedding-3-small`）原生支持指定 1024 维输出；本地特征散列算法统一向 1024 维对齐，消除各层硬编码魔数。
   - Point 结构：Point ID 对应视频的数字唯一标识；Payload 存储元数据快照 `{ "vid": "...", "authorId": "...", "title": "...", "modelName": "..." }`，供召回阶段粗过滤与打散使用。
4. **双模向量化引擎与自动降级路由**
   - 实现 `VectorEmbeddingEngineRouter` 动态策略路由：
     - **主引擎**：`RemoteOpenAiEmbeddingEngine`，调用 OpenAI 兼容规范的 Embedding REST 端点，具备高质量语义理解能力；
     - **降级引擎**：`LocalFeatureHashVectorEngine`，基于视频标题与分类标签的确定性特征散列算法（Feature Hashing），在 JVM 内部通过哈希与 L2 归一化计算 1024 维向量。
   - 路由策略：在未配置 API Key、外部网络异常或接口超时时，系统自动无感知降级到本地散列引擎，确保发布门禁与向量化流水线 100% 可用。
5. **自愈建表与双写冷启动韧性**
   - **自愈探测**：通过 `QdrantClient.ensureCollectionExists` 在启动和写入前主动探测集合，若不存在则自动按 1024 维 Cosine 配置调 API 创建，消除手动建集合的前置运维要求。
   - **本地快照兜底**：在自属 MySQL 中建立 `recommend_video_vector` 账本表，记录每次向量生成的原始向量值、模型名、维度和 Qdrant 同步状态（`PENDING / SYNCED / FAILED`）。若 Qdrant 实例出现损坏或重建，可随时基于该表进行全量或增量冷启动回填。
   - **非阻塞发布门禁**：通过 RabbitMQ 消费 `content.video.submitted` 事件完成向量化处理与 Qdrant 写入，并通过 Feign 回调 `content-service` 的 `task-callback` 推进视频发布门禁。

## 备选方案

| 方案 | 不选的原因 |
| :--- | :--- |
| **Milvus** | 功能完备且支持超大规模分布式，但依赖 etcd、MinIO、Pulsar 等众多外部组件，单机部署内存占用高（数 GB），在当前项目规模下架构过重 |
| **Elasticsearch (dense_vector)** | 本质为全文检索系统，高维向量索引内存开销大，检索与写入吞吐明显弱于专用向量数据库，且不便轻量嵌入 |
| **Pinecone / 云托管商业向量服务** | 属于商业闭源云服务，成本高昂且强制依赖外网连接，无法支持私有化部署和本地离线研发闭环 |
| **MySQL 本地计算余弦距离** | 无向量索引支持，全表扫描计算复杂度为 $O(N)$，无法满足高并发推荐流的毫秒级时延 SLA |

## 后果

- **收益**：
  - 核心个性化召回与探索召回可在毫秒级（通常 < 15ms）完成 top-K ANN 候选视频检索；
  - 架构具备极高的部署韧性：既支持生产环境通过大模型提供高水准个性化推荐，又支持无外网环境下通过本地散列引擎完整跑通全部业务测试；
  - MySQL 向量账本与 Qdrant 索引形成“权威持久化事实 + 高性能检索引擎”双层架构，容灾与重建路径清晰。
- **代价与约束**：
  - 引入了新的独立基础设施依赖（Qdrant），需要监控其容器状态、内存占用及检索 P99 延迟；
  - 向量写入涉及 MySQL 与 Qdrant 双写，存在毫秒级时差，需依赖 `recommend_video_vector` 状态机保证幂等与最终一致；
  - 向量维度变更属于破坏性变更，若未来调整维度需同时重建集合并重新生成历史存量向量。
- **关键提交记录**：
  - `7e8b5a3`：落地视频特征向量化流水线与 Qdrant 双模存储闭环；
  - `059d726`：升级特征向量基准维度至 1024 维并与配置项解耦。
