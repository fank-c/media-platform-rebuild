# ADR 0001: 互动模块采用自属 Outbox 与统一视频交互事件

## 状态

**Accepted（已采纳）**

## 背景

`interaction-service` 是点赞、收藏、播放、分享这些高频互动的唯一所有者，需要把用户行为输出给下游（主要是 `recommend-service`）。有四个约束：

1. **可靠投递**：如果在请求或事务里直接发 RabbitMQ，MQ 出故障会拖垮主链路，还可能出现“业务提交了、消息丢了”或者反过来的情况。
2. **下游未就绪**：推荐侧目前还没有消费队列。现在就投递，消息会因为没有路由被退回，重试会被白白耗尽。
3. **噪音**：客户端会重试、重复点击、频繁发心跳。不去重的话，下游画像会被污染。
4. **计数**：公开计数走的是 Redis 写缓冲加定时刷盘，做不到和明细、事件强一致。

## 决策

1. **自属 Transactional Outbox**
   - 事件先写进本服务独占的 `interaction_outbox` 表，和业务数据在同一个本地事务里落库。
   - 之后由后台派发器用租约抢占记录并投递，要求 Broker Confirm（Broker 确认收到）后才算成功。失败有限次重试，超限记为 `FAILED`，重试沿用原 `eventId`。
   - 不依赖 MQ 的投递顺序。
2. **统一事件契约**
   - Exchange `media.platform.events`（Topic），Routing Key `interaction.video-action.v1`。
   - 使用平台统一信封：`eventId / eventType / eventVersion / traceId / occurredAt / payload`。
   - 载荷只有 `{ userId, vid, action, state }`。
   - 已生效的 `action`：`LIKE`、`STAR`、`PLAY`、`PLAY_COMPLETE`、`SHARE`。
3. **只发真实状态变化**
   - 重复点赞、重复收藏、重复取消、同一会话里的重复心跳，都不产生事件。
   - 每种动作的防重依据必须**持久化在本服务的表里**：状态字段、CAS 条件、幂等键都可以，不能只靠 Redis。
   - 具体判定规则属于实现细节，维护在 [互动模块文档](../modules/interaction.md)，不写进本 ADR。
4. **先存储，后投递**
   - 在推荐侧消费者上线之前，`interaction.outbox.dispatch-enabled` 默认为 `false`：事件只落库，不投递。
   - 消费者上线后，通过配置打开，不需要改代码。
5. **计数最终一致**
   - 公开计数、明细事实、Outbox 事件三者只保证最终一致，不宣称强原子一致。

## 兼容约定

- 在 v1 里新增 `action` 取值或新增字段，算作可加性变更，可以直接加。消费方必须忽略不认识的 `action` 和字段，并按 `eventId` 做幂等处理。
- 删除或改名字段、改变某个 `action` 的含义，都算破坏性变更。这类改动必须发 `v2` 路由，并设兼容期。
- `PLAY_START` 只是代码里的保留常量，目前不会发送，不算已生效的契约。

## 备选方案

| 方案 | 不选的原因 |
| :--- | :--- |
| 事务提交后直接发 MQ | 进程在提交后、发送前崩溃，消息就丢了，也没有补偿手段 |
| 每种动作一个事件类型 | 下游要维护多条绑定。几种动作的载荷结构一样，用 `action` 区分就够了 |
| 把平台 Outbox 做成共享模块 | 会让 `common` 承载业务相关的持久化，违反“服务只访问自属表”的边界 |

## 后果

- **收益**：互动主链路不依赖 MQ 是否可用；事件可以重放、可以审计；网络重试不会重复计数，也不会重复发事件。
- **代价**：
  - 多一张持续增长的表，需要清理策略（未实现）。
  - 分享必须带 `Idempotency-Key`，不带的客户端会收到 `400`。
  - 事件从产生到被消费会有秒级延迟。

## 修订记录

- 补登 `PLAY_COMPLETE`，明确 v1 的可加性兼容约定。
- 把播放防重的具体规则（会话、阈值、冷却时间、CAS 语句）移到模块文档，本 ADR 只保留决策本身。
