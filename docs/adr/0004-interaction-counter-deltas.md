# ADR 0004: 互动公开计数采用事务内增量与后台汇总

## 状态

**Accepted（已采纳）**

## 背景

点赞、收藏、分享、有效播放都有各自的持久化防重状态。旧方案在 Redis 更新计数并定时用绝对值覆盖 MySQL：Redis 无法与业务状态和 Outbox 同事务回滚，提交后的计数调整又可能因进程退出丢失。

## 决策

1. 业务状态真实变化时，在同一 MySQL 事务内写入 `interaction_counter_delta`（含 `vid`、`counter_type`、`delta`、`source_type`、`source_id`）；Outbox 仍按 ADR 0001 独立承担对外领域事件，是否投递不影响计数。
2. 来源追溯、版本化与强约束保障：
   - 增量记录强制携带业务事实来源引用（`source_type` 与 `source_id`），涵盖点赞状态反转版本、收藏明细/级联移除、播放 CAS 时间戳、分享幂等键，建立审计与对账链路；
   - 业务实体状态版本化与唯一键防重：`interaction_like` 与 `interaction_star_item` 维护单调递增的 `version`（初始为 1，每次状态反转或自愈复活递增）；增量来源标识编码为 `like:{likeId}:v{version}`、`star_item:{itemId}:v{version}`。增量流水表建立唯一约束 `uk_counter_delta_source (source_type, source_id)`，构筑数据库层物理防重屏障，既允许合法状态往返，又阻断重试导致的重复记账；
   - 领域模型与数据库 CHECK 约束统一防护：`VIEW` 与 `SHARE` 必须严格大于 0（只增不减）；
   - 快照更新 SQL（`ON DUPLICATE KEY UPDATE`）全部采用 `GREATEST(0, counter + delta)`，防止历史快照在异常负增量或并发逆序下发生负数下溢。
3. 汇总任务对未处理增量按 ID 顺序执行 `SELECT ... FOR UPDATE`，在同一事务中按视频和类型求和、原子更新 `interaction_video_counter`、标记已处理。并发实例在行锁处等待；失败则整批回滚重试。
4. 公开统计只查询已汇总的 MySQL 计数，可接受最多一个或数个批处理周期的延迟；不查询未处理增量。不再运行 Redis 绝对值快照刷盘。
5. 清理任务仅删除已处理且超过保留期的增量。清理 Mapper 注解采用原生 `<` 比较字面量（避免无 `<script>` 下的转义字符错误）。保留期、批大小和间隔可配置；清理失败不得改变计数。

## 代价与约束

- 每次真实计数变化增加一次 MySQL 插入（包含业务来源引用索引支持精准对账）；每批汇总会更新热门视频的计数行，需观察待处理积压及任务失败告警。
- 批内净增量即使出现短暂负值（例如业务提交顺序与自增 ID 分配顺序不同），也会在快照层被 `GREATEST(0, ...)` 截断防穿透，同时借助 `source_id` 可离线追溯对账。
- 切换时必须先确认旧 Redis 脏数据已处理，停止旧刷盘后再启用新写路径；当前构建环境无存量业务数据。
- 当前实现不提供 Redis 公开统计读缓存；Outbox 事件只供下游，不承担本地计数汇总。

## 备选方案

- Redis 绝对值刷盘：无法与业务事务共同回滚，也可能覆盖其他来源的数据库更新，因此停用。
- 请求内直接更新视频计数行：每次有效互动会竞争热门视频的同一行，暂不采用。

## 后果

- 业务状态、计数增量和 Outbox 同事务提交，失败时一同回滚；汇总可重试。
- 公开数字延迟展示；MySQL 需承受真实互动的增量插入及批次汇总写入。
- 观察待处理积压量、最老未处理时间及任务失败，并定期与业务状态对账。

## 验证与回退

- 验证业务失败时增量回滚、重复请求不重复插入、汇总失败不标记完成、多实例不重复计数，以及清理不影响快照。
- 回退时先停新写路径和汇总任务，等待或保留未处理增量；禁止重新启用旧绝对值刷盘覆盖已汇总值。若需恢复旧版本，先对账并安排数据转换。
