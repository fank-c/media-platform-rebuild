# 0006 Refresh 使用 Redis 两阶段条件轮换

- 状态：提议（当前实现决策补录，待维护者确认；非独立验收结论）
- 日期：2026-09-07
- 决策者：项目维护者待确认；文档整理代理补录
- 关联任务/契约：[刷新方案](../reference/auth-refresh-session-atomicity-plan.md)、[认证 HTTP v1](../contracts/http/auth-api-v1.md)

## 背景

原刷新流程消费旧凭据时删除会话，查询账户后重新创建同一 sid；若 logout 在中间执行，刷新可能
重新建立已退出会话。HTTP v1 同时约定旧刷新凭据一旦消费，即使账户校验失败也不可再次使用。
当前工作区已落地两阶段脚本；本记录补齐决策背景，不追认未发现证据的审查或运行验收。

## 决策

拟确认当前实现：auth-service 独占会话键；begin 原子检查索引、会话和 TTL，消费旧索引但保留
会话并设置 rotationId/inflight。账户校验和候选 Token 生成在脚本之外执行；finish 仅在会话仍存在、
归属及本次标记匹配时更新凭据。logout 删除会话后 finish 不可重建；失败只按本次标记条件清理。
登录创建新 sid 与刷新条件更新分离，refresh 不调用无条件创建路径。外部请求不增加 Authorization。

## 备选方案与取舍

- Java 本地锁：不能覆盖多个 auth 实例。
- Redis 分布式锁覆盖整次请求：需要处理持锁超时、续租及旧持有者回写，当前条件脚本更直接。
- 账户检查后一次性轮换：会改变“账户校验失败仍消费旧凭据”的既有约定。

## 影响与风险

不改数据库表、JWT Claims 或消息事件；在既有 Session Hash 中增加短生命周期轮换字段，旧 ready
会话兼容。脚本隔离执行不代表运行错误自动回滚；连接超时可能结果未知，不自动重试或恢复旧凭据。
进程中断可能迫使客户端重新登录。依赖当前单机 Redis 键模型，不宣称支持 Cluster。
不解决全部历史 Access Token 撤销、网关缓存窗口或账户校验后的并发禁用；不宣称完整注销安全。
新旧刷新实现混合处理请求仍有旧逻辑恢复会话风险，不能以字段兼容代替发布排空。

## 验证与回退

按刷新方案用真实隔离 Redis 验证 begin/logout/finish 不同顺序、并发消费、TTL、错误及超时，
并验证 HTTP 契约；测试源码存在不代表已运行。本轮只完成文档静态检查，运行状态见
[测试指南](../guides/testing.md)。部署前停止旧实例处理相关请求并排空在途操作，须另获环境授权。
优先前向修复；必要时受控暂停刷新而允许重新登录，不恢复旧索引、不清空 Redis、不恢复旧快照。
回旧二进制会重新引入竞争风险，不作为等价安全回退；方案中的排空、禁用与回退操作尚未演练。
