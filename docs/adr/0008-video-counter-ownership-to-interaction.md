# ADR 0008: 视频公开计数所有权划归互动服务

## 状态

**Accepted（已采纳，追认）**。该决策在提交 `7b0188c` 重构互动模块与瘦身内容主表时已落地生效，本文补齐架构决策记录。

## 背景

视频的公开交互指标（点赞数、播放量、收藏数、分享数、完播数等）由海量用户的在线交互行为实时触发。在旧架构设计中，这些指标作为字段冗余存储在 `content-service` 的视频主表（`video_content`）中。随着平台架构演进，该设计暴露出以下严重缺陷：

1. **领域职责倒置**：`content-service` 的核心职责是视频元数据（标题、描述、封面、转码规格、时长）、创作者发布流程与审核门禁状态管理，属于“低频变更、强一致性、高价值元数据”领域；而点赞、播放等互动计数属于“超高并发写入、允许最终一致、指标类数据”领域。两类生命周期完全不同的数据混合在同一张表，严重违反微服务单一职责原则。
2. **写热点与数据库行锁瓶颈**：热门爆款视频在播放、点赞高并发场景下，直接竞争 `video_content` 主表的同一行记录锁，造成严重的数据库行锁等待，进而拖慢视频基本信息查询和后台运营管理。
3. **数据一致性裂痕**：点赞记录、收藏明细与播放心跳的物理持久化在 `interaction-service`，而计数字段在 `content-service`。跨微服务无法使用本地事务，网络抖动或异步丢失容易导致“用户明明已点赞，视频计数却没有加”或“取消点赞后计数异常”的长期不一致问题。

## 决策

1. **互动计数所有权完全归属 interaction-service**
   - 视频的所有公开互动计数指标唯一所有者明确为 `interaction-service`。
   - 由互动服务的自属表 `interaction_video_counter` 独占承载计数的累加与快照存储，其他微服务不得建立同名或冗余字段。
2. **彻底瘦身 content-service 主表与实体**
   - 从 `content-service` 的领域模型 `VideoContent`、持久化实体 `VideoContentPO`、Mapper 查询语句及 HTTP 响应 DTO 中彻底移除 `view_count`、`like_count`、`star_count`、`share_count` 等计数字段。
   - 内容服务对外 API（如 `/api/videos/{vid}`、`/api/videos/feed`）仅输出纯净的内容元数据（标题、封面、播放地址、时长、作者 ID、标签、发布时间等）。
3. **前台播放详情由客户端分层请求**
   - 客户端打开视频播放页时，由客户端分别发起两次请求获取不同维度的信息：
     - 请求 `content-service`（`/api/videos/{vid}`）：获取视频播放地址与基本元数据；
     - 请求 `interaction-service`（`/api/interaction/stats/videos/{vid}` 与 `/api/interaction/stats/videos/{vid}/summary`）：获取该视频的公开统计（点赞数、播放量、收藏数等）以及当前登录用户对该视频的个性化交互状态快照（是否已赞、是否已收藏等）。
   - 两套接口在网关之后并行拉取、互不阻塞，任何一方短暂抖动不影响另一方的页面基础渲染。
4. **技术实现机制解耦（引用 ADR 0004）**
   - `interaction-service` 内部如何支撑计数的高性能并发写入、防止负数下溢与防穿透机制，完全遵循 [ADR 0004: 互动公开计数采用事务内增量与后台汇总](0004-interaction-counter-deltas.md)。本 ADR 专注确立**数据所有权与服务边界**的架构划分。

## 迁移路径与验证

1. **代码落地记录**：
   - 核心变更已在 Git 提交 `7b0188c`（2026-09-22，*“feat(interaction): 重构互动模块独立管理视频交互指标并落地播放心跳机制”*）中完成。
   - 该提交在 interaction-service 中新增了 `interaction_video_counter` 及其仓储，并在 content-service 中删除了 5 项计数字段及相关单元测试断言。
2. **存量数据迁移策略**：
   - 当前项目处于微服务重构期，开发与测试环境中无存量生产历史数据，无需执行数据割接或冷数据迁移脚本。
   - 若未来需要从旧系统进行存量数据割接，应遵循如下步骤：
     - 在 interaction-service 部署建表脚本并保持计数汇总服务处于就绪状态；
     - 编写离线迁移 SQL 脚本，从 content 历史快照表中读取当时计数值，批量写入 `interaction_video_counter`；
     - 确认数据一致性后，启用双向验证并完成切换。
3. **验证方式**：
   - 检查 content-service 接口响应：验证 `/api/videos/{vid}` 报文中不再包含任何计数字段；
   - 检查 interaction-service 接口响应：验证 `/api/interaction/stats/videos/{vid}` 正确输出视频各项计数指标。

## 备选方案

| 方案 | 不选的原因 |
| :--- | :--- |
| content-service 消费互动事件并异步更新计数 | 使得两个微服务同时持有计数数据，破坏“单一事实来源（Single Source of Truth）”，且异步时延和重试极易造成长期对账不齐 |
| 在 API 网关层做服务编排组装单次返回 | 使网关承担了业务数据聚合职责（BFF 化），增加了网关层故障面，违背平台轻量网关的定位 |
| 跨微服务分布式事务（如 2PC / Seata）维护两边计数 | 性能开销巨大，引入分布式死锁风险，根本无法支撑高频点赞和播放场景 |

## 后果

- **收益**：
  - 清晰确立了微服务数据所有权，符合领域驱动设计（DDD）边界规范；
  - 彻底消除了内容主表的行锁竞争瓶颈，提升了内容核心库的并发吞吐能力；
  - 计数可以与点赞状态、收藏状态在互动服务内进行统一对账与本地事务防重。
- **代价与约束**：
  - 客户端进入播放页需分别调用内容接口与互动接口，网络调用次数增加（可通过 HTTP/2 多路复用优化）；
  - 跨域查询导致管理后台如果需要同时展示视频标题和播放量，需在管理层做异步聚合或离线报表。
