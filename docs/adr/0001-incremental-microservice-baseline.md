# 0001 渐进式微服务架构基线

- 状态：已接受
- 日期：2026-08-31
- 决策者：项目负责人
- 关联任务/契约：`docs/architecture.md`、`docs/migration-plan.md`

## 背景

Calles 当前为单体视频平台。目标是在不破坏旧系统可用性和回退能力的前提下，逐步拆分认证、
用户、内容、审核、互动和推荐能力，并允许在迁移过程中新增功能。

## 决策

采用 Spring Boot/Spring Cloud 的渐进式微服务架构：

- 使用 Nacos 进行服务发现与配置管理，Spring Cloud Gateway 作为唯一外部入口。
- 使用 `auth-service` 签发和管理自定义 JWT；网关先验签，业务服务保留防御性身份校验。
- 使用 RabbitMQ 承载审核、推荐和其他最终一致性领域事件；事件版本化，消费者幂等。
- 第一阶段保留一个 MySQL 实例和一个数据库，通过服务专属表前缀及访问约束实现逻辑隔离；
  服务稳定后再按所有权物理拆库。
- 采用绞杀者模式迁移：网关按路径切流，未迁移能力保留在单体，迁移单元必须可验证和回退。

## 备选方案与取舍

- **一次性重写和切换**：实现表面更直接，但兼容性、数据一致性和回退风险不可接受。
- **保持模块化单体**：短期成本较低，但无法满足独立演进、异步解耦和后续独立部署的目标。
- **立即独立数据库**：服务自治更彻底，但在边界尚未验证前会放大迁移、运维和数据同步成本。
- **同步 RPC 优先**：调用链更易理解，但会耦合可用性和发布节奏；因此仅保留必要的同步调用。

## 影响与风险

需要维护 Nacos、RabbitMQ、网关、Redis 和 MinIO 等基础设施，并建立配置、消息、日志和健康
检查的运维能力。共享 MySQL 的第一阶段需要严格执行数据所有权，避免跨服务 SQL 回退为新的
单体。JWT 密钥管理、Token 失效、事件可靠投递、消费者幂等和切流回退是首批实施风险。

## 验证与回退

每个服务必须独立构建、启动和注册，并针对其 API、消息和数据迁移执行探针与集成测试。切流
采用网关路由开关；出现异常时立即将对应路径切回单体，并停止新服务写入或按已记录方案回退。
物理拆库仅在逻辑所有权、数据校验和回退演练均完成后评估。
