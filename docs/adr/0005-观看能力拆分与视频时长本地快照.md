# ADR 0005: 观看能力按进度 / 会话 / 资格 / 凭据拆分，并使用视频时长本地快照

## 状态

**Accepted（已采纳）**

## 背景

`interaction-service` 原先把观看进度、历史展示、会话累计、播放量防刷和完播防重全部压在一张 `interaction_watch_history` 上，用 `session_play_emitted`、`eligible_for_next_play`、`last_valid_play_at` 三个字段加 CAS SQL 表达。四个问题：

1. **语义混装**：`eligible_for_next_play` 同时表示"本会话达到 30%"和"下一会话可以计数"，阅读和测试都要靠上下文猜。
2. **时长口径不可信**：视频时长来自客户端上报的 `videoDuration`，客户端可以直接影响播放量门槛与完播判定；增量也只做了单次截断，没有和真实心跳间隔比对。
3. **并发依赖外部组件**：心跳用 Redisson 分布式锁串行化，锁超时还要走"只读降级"，链路复杂且降级会丢弃本次时长（见 [ADR 0003](0003-interaction-redisson-distributed-lock.md)）。
4. **防重依据分散**：领域布尔字段、应用层判断、CAS 条件和分布式锁四层共同防重，无法单独验证任何一层是否足够。

同时 `content-service` 的视频发布事件 `content.video.published` 载荷中不含 `duration`，互动服务无法从既有事件获得可信时长。

本重构发生在功能服务设计阶段：观看链路尚未对外提供稳定接口、没有存量业务数据、也没有已上线的消费方。因此旧实现**直接删除**，不设兼容期（见"备选方案"与"修订记录"）。

## 决策

1. **按职责拆表**，观看能力不再由单一实体承担：
   - `interaction_video_snapshot`：视频时长本地快照，是播放量门槛与完播判定的唯一时长口径；
   - `interaction_watch_progress`：断点续播、历史展示与"最近一次计入播放量时间"；
   - `interaction_watch_session`：本会话服务端校验后的有效观看时长与会话内状态；
   - `interaction_watch_event_claim`：播放量与完播事件的最终防重依据。
   - 旧表 `interaction_watch_history` 与旧领域实体、旧 CAS Mapper 全部删除，"播放资格"不再落成独立表，而由 `watch_session.qualified`（会话级）、`watch_progress.last_view_claimed_at`（用户×视频级）与 `watch_event_claim`（事件级）共同表达。
2. **事件凭据作为唯一防重屏障**：`uk_watch_event_claim (user_id, vid, session_id, event_type)`。凭据插入成功才允许写 Outbox 与播放量增量，三者同一本地事务。
3. **并发控制回到数据库**：心跳先 `SELECT ... FOR UPDATE` 锁定 `interaction_watch_progress` 行，首次心跳的并发插入由唯一键兜底并按冲突重试为行锁读取。由此**移除 Redisson 依赖、`RedisLockService` 与观看链路的只读降级分支**，ADR 0003 被本 ADR 取代。
4. **时长只信服务端**：客户端 `deltaDuration` 必须同时通过三重上限才计入——
   - 单次上限（默认 15 秒）；
   - 服务端时间差上限：不超过"参考时间 + 容差"（容差默认 2 秒）。参考时间取本会话上一次有效心跳时间；会话刚创建时取进度表的上一次心跳时间，因此**没有任何历史的新用户首次心跳最多只能计入一个容差长度**；
   - 会话视频时长剩余量。
   播放位置只用于断点，跳跃距离永不计入时长。
5. **门槛在会话创建时固定**：`duration_snapshot` 与 `qualification_threshold` 为会话级快照，视频元数据后续变化不影响进行中的会话。
6. **时长快照由事件驱动**：`content-service` 新增独立事件 `content.video.metadata`（载荷含 `duration` / `metadataVersion` / `status`），在发布事务内与 `content.video.published` 一并写入 Outbox；`interaction-service` 订阅 `interaction-service.video-metadata` 并幂等写入快照。**不做跨服务同步调用，也不扩展既有发布事件载荷**（后者会改变推荐侧入池事件的既有语义）。
7. **事件契约不保留版本号**：点赞、收藏、分享、观看量资格与完播共用一条路由 `interaction.video-action`（Routing Key 等于事件类型，`eventVersion = 1`），载荷按行为族扩展字段。不采用 `interaction.video-action.v1` / `.v2` 双路由的原因：本服务从未开启投递、也没有任何消费方，不存在需要兼容的历史契约。后续真需要破坏性变更时，再按 ADR 0001 发新路由。
8. **只保留一个 HTTP 入口并收紧协议**：`POST /api/interactions/videos/{vid}/heartbeat`。通过入参严格区分为起播与后续心跳两种形态：
   - 起播必携 Header `Idempotency-Key`，`sessionId` 为空，`sequence=0`，`deltaDuration=0`。直接校验发布状态与 6 小时冷却计入播放量（来源为 `WATCH_PLAY:watch_session:{sessionId}`）；活跃未过期会话返回 409 `WATCH_SESSION_ACTIVE`；
   - 后续心跳必传 `sessionId` 与递增 `sequence>0`，达到 `max(5s, 30%)` 时独立由凭据防重发出 `WATCH_VIEW_QUALIFIED` 领域事件，不再重复计播放量、不读改冷却；会话错位/过期返回 409 `WATCH_SESSION_INVALID` / `WATCH_SESSION_EXPIRED`。
9. **删除历史只隐藏展示**：删除只把 `deleted` 置 1，记录不物理删除，因此播放量冷却与事件凭据不会被"删除后重看"重置。物理删除只发生在保留期外的清理任务中。

## 代价与约束

- 心跳从"一次真写入 + CAS"变为"行锁读取 + 会话与进度更新 + 可能的凭据插入"，正常路径多一到两次 UPDATE；换取了可验证的单一防重依据。
- **首次心跳与长时间空闲后的首次心跳会少算时长**：没有任何历史时首次最多计入一个容差长度。这是有意的保守取舍（宁可少算不可多算）。
- 会话与凭据按观看次数增长，必须有保留期清理任务，且清理顺序必须是"先解除活跃引用再删除会话"，否则仍被进度引用的会话无法删除。
- `interaction-service` 首次引入 RabbitMQ 消费侧：新增队列、绑定、死信交换机与死信队列、消费重试配置。元数据事件缺失或非法时**降级为只保存断点、不产生播放量与完播**，因此死信积压必须在告警口径内可见。
- 旧实现被删除，**不能再靠配置切回旧模型**；回退只能回滚代码版本。新表数据不会因此丢失，可保留复用。
- 视频时长只由发布事务发出的元数据事件建立：如果 content 侧队列绑定尚未声明就先发布事件，该事件会因无绑定丢失，需要重放。

## 备选方案

| 方案 | 不选的原因 |
| :--- | :--- |
| 继续用 `eligible_for_next_play` 表达跨会话资格 | 该字段把两个语义压在一起，正是复杂度来源；无法为"每会话一次"提供可单独验证的依据 |
| 保留旧实体与旧表，靠 `model-mode` 三模式 + 兼容期渐进切换 | 观看接口与客户端都还没有稳定契约，没有存量数据，兼容期只购买复杂度：两套并发控制、两套事件、影子分支与回退开关都成了纯负担 |
| 心跳时同步调用 content-service 取时长 | 引入同步跨服务依赖，视频详情不可用时会拖垮心跳；且违反"不跨服务同步查元数据"的边界 |
| 扩展 `content.video.published` 载荷加入 `duration` | 可加性变更虽然不破坏消费方，但会把"发布上线"与"元数据快照"两件事绑在一个事件上，后续元数据演变仍要再拆一次 |
| 把观看事件并入 `interaction.video-action` | 按 ADR 0001 的兼容约定这属于破坏性变更，前提是该契约已发布。本服务从未开启投递、也无消费方，所以这个顾虑不存在：直接用不带版本后缀的单路由（见决策 7）|
| 单纯放宽时间容差（例如 10 秒）以简化实现 | 容差即"每个请求可白送的时长"，容差越大防刷越弱；正确做法是收紧容差并用参考时间兜住会话边界 |

## 后果

- 播放量、完播、观看进度三者各自有唯一的持久化归属，判定逻辑可以用纯领域单元测试覆盖。
- 观看心跳不再依赖 Redis 可用性，工程也少了一个第三方依赖（Redisson）。
- 事件族只有一条路由、一个载荷类型，消费方无需为多版本路由维护多条订阅；代价是消费方必须按 `action` 分支取字段。
- 互动服务运行期多一条入站队列与一套死信出口，需要新的事件发布顺序约束：**先部署消费侧声明队列，再开发布侧**。
- 公开播放量仍走 ADR 0004 的事务内增量与后台汇总，本 ADR 不改变计数聚合机制。

## 验证与回退

- 验证：单元测试覆盖 30% 门槛、5 秒最低门槛、冷却窗口与冷却后补计、每会话一次播放量与完播、重复与乱序序号、位置跳跃、无快照降级、删除历史不重置冷却、以及增量三重上限；集成测试需显式开启 `WATCH_HEARTBEAT_IT_ENABLED=true` 并连接本地 MySQL，覆盖元数据事件幂等、凭据唯一键防重与重复序号零写入。
- 回退：回滚代码版本；新表可保留不删。`interaction.outbox.dispatch-enabled` 与 content 侧的投递开关独立，故障时可先暂停投递。

- 2026-09-26 初稿：按"新增结构 → 影子运行 → 切换 → 观察 → 清理"设计，保留旧模型与 `model-mode` 三模式开关，新模型提供 `legacy` / `shadow` / `v2` 三种取值。
- 2026-09-26 修订：确认观看链路处于功能设计阶段、无存量数据、无已上线调用方，因此删除兼容期设计——直接移除旧实体、旧表、旧 CAS、Redisson 依赖与模型开关。同时把增量时间容差从 10 秒收紧到 2 秒，并把新会话的参考时间改为进度表上一次心跳时间。
- 2026-09-26 再修订：去除所有版本号命名。事件路由键由 `interaction.video-action.v1` / `.v2` 收敛为 `interaction.video-action`（不再按 `eventType + .v + eventVersion` 推导）；`PLAY` / `PLAY_COMPLETE` / `PLAY_START` 三个 action 直接删除，观看量改用 `WATCH_VIEW_QUALIFIED` / `WATCH_COMPLETED`；HTTP 入口只保留 `POST /api/interactions/videos/{vid}/heartbeat`，删除 `/v2/...` 路径；两种载荷合并为单一 `VideoActionPayload`；入站队列去掉 `.v1` 后缀。同时把决策 6 里的队列名同步更新。
- 2026-09-27 修订：观看播放量与行为事件解耦。起播（零秒心跳开启会话）立即校验视频已发布准入与 6 小时冷却窗口记录播放量（`WATCH_PLAY:watch_session:{sessionId}`）；彻底解耦 5 秒/30% 门槛；合格观看事件 `WATCH_VIEW_QUALIFIED` 纯粹由有效观看时长驱动并不再影响播放量；起播强校验 Header `Idempotency-Key`，会话状态冲突明确抛出 409（`WATCH_SESSION_ACTIVE` / `WATCH_SESSION_INVALID` / `WATCH_SESSION_EXPIRED`）；快照更新引入行锁原子 CAS 约束杜绝并发降级，保留期清理会话增加 `NOT EXISTS` 存活引用保护与确定性解绑排序。
