# 0007 file-service 第一阶段私有 MinIO 文件能力

- 状态：已接受
- 日期：2026-09-07
- 决策者：项目维护者、实施代理
- 关联任务/契约：[文件服务执行方案](../reference/file-service-phase-one-plan.md)、[文件 HTTP v1](../contracts/http/file-api-v1.md)

## 背景

原架构将文件元数据和对象存储编排笼统归入 content-service，无法让上传确认、对象 key、私有读取和存储故障边界拥有明确所有者。第一阶段需要可独立验证的小文件能力，但尚未完成旧单体文件盘点、数据回填、业务引用、跨服务读取或真实环境直传门槛。

## 决策

新增 file-service，独占 `file_asset` 和 `file_*` 数据前缀，首期只注册 MinIO。提供普通 multipart 上传、预签名 PUT 初始化与服务端异步确认、本人元数据查询、短期 GET 签名、远端先删后逻辑删除，以及默认关闭的过期清理。业务 API 仍经网关；对象数据 PUT/GET 仅作为短期预签名的受控传输例外。`FileContentService` 只在 file-service 进程内可用，不作为跨服务 Java 接口。

## 备选方案与取舍

1. **继续归属 content-service**：减少一个模块，但会把内容发布与对象协议、私有文件生命周期耦合，未采用。
2. **一开始支持多种 S3 存储、版本化、对象 COPY、分布式补偿和 MQ**：能覆盖更多场景，但超出当前隔离验证范围，未采用。
3. **全部对象数据经网关中转**：避免直连例外，但失去直传收益并提高网关负载，留待真实环境入口决策。

## 影响与风险

本方案引入 MinIO SDK 与 file-service 模块，未引入新基础设施。对象 I/O 与数据库事务不具原子性；签名复用、对象覆盖、删除/确认竞争、迟到 PUT 和孤立对象不能被数据库 CAS 完全解决。业务 API 依赖网关可信网络，直连服务伪造身份 Header 的防护是部署前提。真实环境必须在私有 bucket、TLS、CORS、最小权限、签名端点、完整性与引用保护完成验证后另行授权。

## 验证与回退

先在无冒号隔离副本完成编译、单元测试、YAML 与 Compose 静态校验；随后仅在授权隔离 MySQL 和私有 bucket 验证 DDL、SDK 签名、A/GET/B 确认、并发 CAS、删除/清理竞争和网关直连防护。未对外启用时可停止 file-service、确认和清理任务，并撤销新增模块/路由/配置；保留 `file_asset` 和对象用于排查，禁止通过 DROP 表、全桶删除或伪造 COMPLETED 状态回退。远端删除过的对象不保证恢复。
